Conversation Memory & Compression

How gamemAIster keeps a long-running TTRPG session inside a finite LLM context window without losing the campaign's history.

Read this if: you're onboarding, or you haven't touched src/brain/chat.py in a year and need to remember why there are three separate compression mechanisms instead of one.

Accuracy note: file/line references below reflect the code as of writing. They drift — treat them as a map to start your search, not as guaranteed line numbers.

1. Why this exists

A TTRPG campaign can run for dozens of sessions. The story LLM (SummaryChat) can only ever see a bounded context window per turn, and the GM model behind it can be a small/local model with a genuinely tight budget — so the raw chat transcript cannot just be replayed in full forever. Something has to compress "everything that happened" into something small enough to keep injecting every turn, without the GM forgetting who the NPCs are, where the party is, or what they promised three sessions ago.

The system splits that compression into three independent lenses, each answering a different question about the same raw play text, rather than one mechanism trying to do everything at once.

2. The three lenses Implemented

Entities

"Who/what exists?" — atemporal knowledge base
  • One row per named person/place/item/faction/etc., with a running summary
  • Deduplicates and fuses entities the model realizes are the same thing
  • Cross-references the mission's NPC roster so a character isn't re-invented under a different name

Scenes

"What happened, in order?" — structured chronological log
  • Splits play into discrete scenes (location/time/focus changes)
  • Each scene: title, location, characters present, exhaustive summary, completed flag
  • Most "blow-by-blow" detail lives here, not in the narrative summary

"What's the story so far?" — running narrative prose

3. The pipeline

All three lenses are computed from the same raw text and run independently — none of them sees the others' output.

All three calls run in parallel via a ThreadPoolExecutor — they're independent, so there's no reason to serialize them.

Getting it back into the story prompt

On the next turn, SummaryChat._build_messages() injects the current summary/scenes/entities via summary_provider.txt (the {SUMMARY}/{SCENES}/{ENTITIES} placeholders), positioned before the still-unsummarized tail of raw interaction history — those most-recent turns are always sent verbatim, never compressed.

4. Staying consistent with the mission's NPC roster Implemented

Missions ship with a keyNPCs roster (name/role/affiliation/secrets) written before play starts. Without help, the entity/scene compressors only see raw narration — if the GM calls someone "the High Priestess" for a few turns before ever saying "Devana", they have no way to know it's the same person as roster entry Devana, and can fork a duplicate identity.

  • known_npc_roster (name/role/affiliation only, no secrets) is passed into both extract_entities() and scene_summary() every cycle, with prompt instructions to use the roster's exact name instead of inventing one.
  • Entity.matched_key_npc is a real, name-independent link the model sets when it recognizes a roster match. crud.update_entities() resolves incoming entities against existing rows by this field first, name second — so even if the model still uses an inconsistent display name one cycle, storage merges onto the same row instead of forking a duplicate.
  • The live story prompt has an analogous, separate mechanism — _flag_active_key_npcs() annotates the mission JSON's roster entries with _activeNpcOverride when an active NPC sheet is matched, so the model isn't handed two silently conflicting descriptions of the same character.

5. Bounding summary growth: the ledger/digest split Implemented

The narrative summary used to be a single, append-only block of prose — text_summary_prompt.txt preserved established content and only ever added to it, by design, so nothing got silently lost in a rewrite. The tradeoff: nothing ever shrank it either. Over a long campaign, that one block — re-injected into the story prompt every single turn — would grow forever, which is exactly the failure mode small/local models with tight context windows can't absorb. The current design splits it into two pieces to fix that without giving up the append-only guarantee:

  1. 1
    A full, append-only ledger in storage (the SummaryMemory.summary column, unchanged) — the permanent, lossless record. This is still the source of truth forever; nothing about it shrank or got rewritten.
  2. 2
    The per-cycle append is deterministic, not model-trusted. The model is never handed the growing ledger and told "don't touch this part" — that was risky for weak models, which can truncate/drift/ duplicate text they're told to leave alone. SummaryMemory.summarize() only ever recaps the new current_events chunk (grounded by the latest digest + the last paragraph of the ledger, for coherence — see step 4); _try_summarize() then does ledger = ledger + recap as plain string concatenation, in code, not the model. Zero information loss is a structural guarantee, not an instruction the model has to honor.
  3. 3
    The raw ledger stops being injected once it crosses a size budget. SummaryMemory._refresh_digest() is a separate, infrequent pass: once the ledger's token count grows past digest_budget_tokens since the last refresh, it condenses the whole ledger into a short, bounded "story so far" blurb (text_digest_prompt.txt). That digest — not the raw ledger — is what SummaryChat._build_messages() injects via SummaryMemory.injected_summary from then on, and it gets refreshed again each time the ledger grows past the next threshold. The injected size stays roughly constant forever; the ledger underneath keeps growing, untouched, in storage.
  4. 4
    The digest also grounds the next cycle's recap — combined with the literal last paragraph of the ledger (_last_paragraph(), no LLM call). The digest gives broad arc continuity (threads from many sessions back); the last paragraph gives precise recency (what was appended right before this chunk). Both stay bounded regardless of campaign length, and the prompt labels them distinctly (story_so_far vs. most_recent_events) rather than as one blob — a weak model is more likely to conflate them otherwise.
  5. 5
    (Optional, complementary, not implemented) Scene-tiered recap for injection. Scenes are already a structured chronological backbone. Inject full detail only for the last few scenes; for older completed scenes, substitute a short, separately-generated 1-2 sentence recap (a narrow, easy task — much safer for weak models than asking for holistic "what's still relevant" judgment over the whole campaign). Full per-scene detail would stay in the DB untouched, same as the ledger. Worth revisiting if the digest alone ever proves insufficient.

Cycle 10 — grounded by the digest, not the raw ledger
digest (from cycle 9)
"The runners completed Mr. Johnson's data-chip job at Ares Tower, extracting Dr. Chen in the process. Chen has since revealed hidden loyalties to a rival corp, and the team is currently laying low from Ares retaliation while deciding whether to trust her."
last paragraph of ledger — literal recency anchor
"…the team relocated to a safehouse in Touristville and debated turning Chen over to her former employer for a reward."
current_events (new chunk)
"A fixer named Cryptic contacts the team with a lead on a Renraku research lab that might be looking for people with Chen's exact skill set."
recap — produced by summarize()
"Cryptic approached the team about a potential Renraku research-lab job that might intersect with Chen's background."
ledger (after) — appended onto the full cycle-9 ledger, not the digest
[…entire cycle-9 ledger text…] "Cryptic approached the team about a potential Renraku research-lab job that might intersect with Chen's background."

The digest stays small and roughly constant in size forever. The ledger underneath keeps growing exactly as it does today, in full — it's just no longer what gets repeated into every single turn's prompt.

Net effect: the compression LLM never processes more than one bounded chunk at a time, the story LLM never receives an unbounded blob, and nothing is ever destroyed — only what's injected is capped; full fidelity always remains in storage.
